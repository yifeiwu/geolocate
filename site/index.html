Australian Suburb Neighbourhood API

Given a suburb and postcode, returns every Australian suburb within N hops of connectivity — where distance is measured by how many shared boundaries separate two suburbs, not by kilometres. Every neighbour carries both its hop count and its straight-line distance, so you can filter either way.

How distance works

Suburb boundaries come from Geoscape Administrative Boundaries, the official gazetted locality boundaries. Two suburbs are directly connected (1 hop) when their polygons share a boundary line of at least 1 metre.

  • 1 hop — the polygons share a boundary.
  • 2 hops — reachable via one intermediate suburb.
  • 3 hops — reachable via two intermediate suburbs.

Corner contact does not count. Four suburbs meeting at a single point are all 2 hops apart, never 1. In the current build, 1,047 corner-only contacts were rejected this way.

River-separated suburbs are not adjacent. Geoscape models waterways as gaps between localities, so for example the Melbourne CBD and Fitzroy are ~144 m apart across the Yarra and are not directly connected. Fitzroy is instead adjacent to Carlton, East Melbourne and Collingwood.

km and hops are independent. A suburb 2 hops away can be closer in kilometres than one 1 hop away — long thin corridor suburbs are the usual case. Never infer one from the other.

Endpoints

Neighbours for one suburb

One file per locality, named <slugified-name>-<postcode>. Fully self-contained — every neighbour carries its own name, postcode, state, hop count and distance. There is no hop parameter: the file always holds the same fixed neighbourhood, and hops and km are there so you can filter it however you like.

GET /api/n/parramatta-2150.json
{
  "suburb": "Parramatta",
  "postcode": "2150",
  "state": "NSW",
  "locality_id": "loc581d5d75cd4f",
  "postcodes": ["2150", "2116"],
  "centroid": { "lat": -33.81397, "lon": 151.00688, "kind": "geometric" },
  "area_sqkm": 5.48,
  "max_distance": 3,
  "isolated": false,
  "truncated": false,
  "neighbours": [
    { "suburb": "Harris Park", "postcode": "2150", "state": "NSW", "hops": 1, "km": 1.0 },
    { "suburb": "Mays Hill",   "postcode": "2145", "state": "NSW", "hops": 1, "km": 1.8 }
  ]
}

Where a name and postcode collide across a state border the slug gains a state suffix, for example cottonvale-4375-nsw and cottonvale-4375-qld. A locality with no neighbours returns "isolated": true and an empty list.

Search index

GET /api/index/p.json

Sharded by the first letter of the locality name, so typeahead never downloads the whole dictionary.

Bulk data

GET /data/suburbs.json   # dictionary: id -> name, state, postcodes, centroid, cx, cy
GET /data/graph.json     # raw adjacency: id -> [neighbour_id, centroid_km, shared_boundary_km]

These two files carry the whole dataset: graph.json is every adjacency edge (43,373 of them, stored in both directions), and suburbs.json maps each id to its name, state, postcodes and centroid. Together they are smaller than the per-suburb files and support any hop distance via bfs().

Client library

assets/neighbours.js — no dependencies, works in the browser or Node.

<script src="assets/neighbours.js"></script>
<script>
  const api = createClient();
  const r = await api.query('Parramatta', '2150');
  console.log(r.neighbours);          // every neighbour the build precomputed
  console.log(await api.search('parra', 10));
</script>

Each file holds one fixed neighbourhood, so there is no hop argument — every record carries both hops and km, so filter the list yourself: 

const withinKm = 5;
const near = r.neighbours.filter(n => n.km <= withinKm);
const direct = r.neighbours.filter(n => n.hops === 1);

For hop counts beyond the precomputed maximum, load the raw graph and expand client-side — it is a few hundred KB and a breadth-first search takes milliseconds: 

const { graph, suburbs } = await api.loadGraph();
const id = Object.keys(suburbs).find(k => suburbs[k].slug === 'parramatta-2150');
api.bfs(graph, id, 6, suburbs);   // any depth

Pass the full dictionary from data/suburbs.json. bfs() measures centroid-to-centroid from its cx/cy; without them it falls back to the per-edge distance, which is the distance to the previous hop and is badly wrong past hop 1.

Cross-border localities

Five localities share both a name and a postcode across a state border, so name+postcode alone is not unique. Their slugs carry a state suffix. Pass the state as the third argument, or fetch by slug: 

await api.query('Texas', '4385', 'QLD');   // texas-4385-qld
await api.getSuburbBySlug('texas-4385-nsw');

await api.query('Texas', '4385');
// throws err.code === 'AMBIGUOUS_SUBURB', err.slugs === ['texas-4385-nsw', 'texas-4385-qld']

getSuburb() tries the plain <name>-<postcode> slug first and only falls back to the search index when that misses, so ordinary lookups cost a single request. The affected pairs are Cottonvale 4375, Jervis Bay 2540, Mingoola 4380, Mungindi 2406 and Texas 4385.

Caveats

  • Centroids can fall outside a suburb. A geometric centroid of a concave or multi-part polygon is not necessarily inside it. Where that happens the anchor is replaced by a representative point of the largest part and centroid.kind is "fallback". This affects … localities, overwhelmingly remote pastoral areas.
  • Postcodes come from ABS Postal Areas, a mesh-block approximation, not Australia Post. A large rural locality can span several postcodes; postcodes lists all of them and postcode is the dominant one.
  • Postcode boundaries are frozen at the ASGS edition used. The build uses the newest published edition and probes for a newer one each run.
  • Isolated localities are real. Islands and remote stations with no sharing locality return an empty neighbour list rather than an error — … localities in the current build, including Lord Howe Island and French Island.
